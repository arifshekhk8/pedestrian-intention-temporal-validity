১. আমরা কী নিয়ে কাজ করছিলাম

আমরা PIE dataset নিয়ে কাজ করছিলাম — গাড়ির সামনে ক্যামেরা লাগানো, রাস্তায় পথচারীদের ভিডিও। লক্ষ্য: একজন পথচারী রাস্তা পার হবে কি না, ঘটনার আগেই বলে দেওয়া।

Model যা দেখে

  • ১৬ ফ্রেমের একটা ছোট window (প্রায় আধা সেকেন্ড)
  • প্রতি ফ্রেমে ৫টা সংখ্যা — পথচারীর bounding box [x1, y1, x2, y2] আর গাড়ির গতি vehicle_speed
  • কাঁচা pixel স্থানাঙ্ক (1920×1080), image size দিয়ে ভাগ করা নয়

Data ভাগ (কখনো এলোমেলো ভাগ নয়)

Recording set অনুযায়ী স্থির ভাগ, যাতে একই পথচারী দুই ভাগে না পড়ে: train = set01/02/04, val = set05/06, test = set03।

Model ছিল একটা BiLSTM। ফলাফল আসছিল AUC ≈ 0.93 — বেশ ভালো দেখাচ্ছিল। সমস্যা শুরু হলো যখন আমরা প্রশ্ন করলাম — আসলেই কি model ভবিষ্যদ্বাণী করছে, নাকি অন্য কিছু করছে?

২. সমস্যা ১ — Temporal Contamination (সময়গত দূষণ)

সমস্যাটা কী

যাচাই করে দেখলাম, যে ১৬ ফ্রেমের window দেখে model "ভবিষ্যদ্বাণী" করছে — সেই window-এর ভেতরেই পথচারী ইতিমধ্যে রাস্তা পার হওয়া শুরু করে ফেলেছে।

উপমা: পরীক্ষার আগে প্রশ্নপত্র ফাঁস হয়ে যাওয়া। ছাত্র ভালো নম্বর পাচ্ছে, কিন্তু সেটা তার জ্ঞানের প্রমাণ নয়।
Model ভবিষ্যদ্বাণী করছে না — সে উত্তরটা দেখে ফেলছে।

PIE-তে 369টা window (crossers-এর 64.7%) ছিল পুরোপুরি crossing-এর ভেতরে — মানে ঐগুলোতে কোনো ভবিষ্যদ্বাণীর প্রশ্নই ওঠে না, ওটা নিছক শনাক্তকরণ।

এটা হলো কেন

PIE-র annotation-এ দুইটা আলাদা জিনিস আছে:

  • crossing — পথচারী এখন পার হচ্ছে কি না
  • crossing_point — পার হওয়া শুরু হয়েছে কোন ফ্রেমে

প্রচলিত code শুধু crossing পড়ে, crossing_point কখনো পড়ে না। তাই window গুলো track-এর শেষ থেকে গোনা হয় — এবং crossing-এর উপর গিয়ে পড়ে।

গুরুত্বপূর্ণ: এটা কারো bug নয় — এটা পুরো field-এর একটা গঠনগত ভুল। এজন্যই এটা paper-এর যোগ্য। ধারণাটা PCPA (WACV 2021) আগেই নাম দিয়েছে; কিন্তু কেউ কখনো এর পরিমাণ মাপেনি — সেটাই আমাদের অবদান।

বাইরের সমর্থন

GTransPDM (IEEE SPL 2025), Fig. 4 — তারা TTE ব্যবধান কমাতে কমাতে দেখেছে: "TTE = 0-তে accuracy ও F1 পৌঁছায় 99.32% ও 98.73%।" মানে ব্যবধান শূন্য হলেই কাজটা প্রায় নিখুঁতভাবে সমাধানযোগ্য হয়ে যায়। ওই paper-এর এই তর্কে কোনো পক্ষ নেই — তবু তারা একই ঘটনা দেখাচ্ছে। আমাদের audit ব্যাখ্যা করে কেন।

৩. সমাধান ১ — Event-Anchored Protocol

আমরা window বানানোর নিয়ম বদলে দিলাম।

 নিয়ম
পুরনোtrack-এর শেষ থেকে পিছিয়ে গিয়ে window নাও
নতুনcrossing_point-এ anchor করো, তারপর window বসাও তার ৩০–৬০ ফ্রেম আগে

এতে crossing window-এ ঢোকা গঠনগতভাবেই অসম্ভব হয়ে যায়।

আমরা দুইভাবে যাচাই করেছি

  1. ফলাফল পরিষ্কার কি না: নতুন dataset-এ 4,906 window-এর মধ্যে 0টা দূষিত — কোনো window-এ একটাও crossing ফ্রেম নেই।
  2. পুনরুৎপাদনযোগ্য কি না: কাঁচা PIE থেকে dataset-টা হুবহু (bit-exact) আবার তৈরি হয়।

৪. পরিষ্কার করার পর যা দেখলাম

(ক) "সহজ shortcut" অনেকটা গায়েব হয়ে গেল

(খ) চারটা model family — একই নিয়মে তুলনা

আমরা চারটা family তুলনা করলাম — BiLSTM, Transformer, GRU, আর un-gated vanilla RNN — সবাইকে একই engine, একই device (CPU), একই ৫টা seed, একই class weight (1.682), একই checkpoint নিয়ম দিয়ে। পরিসংখ্যান: পথচারী-ভিত্তিক bootstrap (B = 10,000) + Holm সংশোধন, ৩০টা তুলনা।

কেন এটা গুরুত্বপূর্ণ: এটা এই literature-এর সব architecture-দাবির একটা সীমা টেনে দেয় — আমাদের নিজেদের দাবিসহ।

৫. সমস্যা ২ — Class-Dependent Sampling Phase

এখানেই গল্পটা সবচেয়ে আকর্ষণীয় হয়।

প্রথমে: Negative class কেন লাগে?

একটা স্বাভাবিক প্রশ্ন — "যারা পার হবে না তাদের নিয়ে ভাবছি কেন?"

ভাবুন — যদি dataset-এ শুধু crossing পথচারী থাকত, model কী শিখত? সে শিখত "সবাইকে হ্যাঁ বলে দাও" — ১০০% accuracy, কিন্তু সম্পূর্ণ অকেজো।

মূল কথা: Model "crossing behaviour" শেখে না। Model শেখে — "যে দুইটা দল আমাকে দেখানো হয়েছে, তাদের মধ্যে পার্থক্যটা কী?"
এবং সে সবচেয়ে সহজ পার্থক্যটা ধরে। পার্থক্যটা অর্থপূর্ণ কি না, তার কোনো মাথাব্যথা নেই।

আমাদের 4,906 window-এর মধ্যে 3,258টাই negative — অর্ধেকের বেশি। এরাই model-কে বলে দেয় "না" জিনিসটা দেখতে কেমন। ওরা ভুল হলে model-ও ভুল।

Negative-দের window আসলে কোথা থেকে আসে?

Positive-দের জন্য সহজ — crossing একটা আসল ঘটনা, ওটার ৩০–৬০ ফ্রেম আগে window বসাই।

কিন্তু negative-দের? তাদের তো কোনো ঘটনাই নেই! তাহলে window কোথায় বসাব?

প্রচলিত code (PIE-র নিজের extract_tracks_tte) যা করে: track-এর শেষ ফ্রেম − ২। আমরা মেপে দেখেছি — যে ৮৩৩ জন non-crossing পথচারী পরিষ্কার dataset-এ আছে, তাদের ৮২৪ জনের (৯৮.৯%) ক্ষেত্রে এই দূরত্ব ঠিক ২ ফ্রেম।

এখন প্রশ্ন করুন — একজন পথচারীর annotation track শেষ হয় কখন? যখন সে ক্যামেরা থেকে হারিয়ে যায়। আর সে হারিয়ে যায় কখন? যখন গাড়ি তাকে পাশ কাটিয়ে চলে যায়।

আমরা leakage সত্যিই ঠিক করেছি — 4,906টার একটাতেও crossing নেই, যাচাই করা। কিন্তু তারপরেও data-তে AUC 1.0000-এর একটা লুকানো সংকেত রয়ে গেছে।
মানে: যে সমাধানটা সবাই যথেষ্ট মনে করবে, সেটা যথেষ্ট নয়।

Model এটা কীভাবে ধরে ফেলে?

Model তো "কত ফ্রেম বাকি" দেখে না — সে শুধু ৫টা সংখ্যা দেখে। কিন্তু গাড়ি যখন কারো পাশ কাটানোর ১–২ সেকেন্ড আগে থাকে, তখন:

  • তার bounding box খুব দ্রুত বড় হচ্ছে (কাছে চলে এসেছে)
  • box ফ্রেমের কিনারার দিকে সরছে
  • গাড়ির গতির একটা নির্দিষ্ট ধরন থাকে

Model এগুলো দেখে পরোক্ষভাবে ওই লুকানো সংকেতটাই শিখে ফেলে। সে ভাবছে না "এই লোক পার হবে না" — সে ভাবছে "এই recording এক্ষুনি শেষ হয়ে যাবে"।

উপমা: আপনি ছবি দেখে বলতে চান কোন ছাত্র পাশ করবে।
পাশ করা ছাত্রদের ছবি তুললেন পরীক্ষার ৬ মাস আগে, ক্লাসরুমে।
ফেল করা ছাত্রদের ছবি তুললেন তাদের কলেজ ছাড়ার শেষ দিনে, গেটের সামনে ব্যাগ হাতে।

Model ৯৫% accuracy পাবে। কিন্তু সে শিখেছে "গেটের সামনে ব্যাগ হাতে = ফেল" — পড়াশোনা নয়। বাস্তবে চালালে সম্পূর্ণ ব্যর্থ হবে।

৬. AUC = 1.0000 আমরা কীভাবে মাপলাম

প্রথমে একটা ভুল ধারণা সরাতে হবে

অনেকে ভাবেন AUC মানেই model-এর স্কোর। আসলে তা নয়।

AUC-র জন্য কোনো model লাগে না। AUC শুধু মাপে — "একটামাত্র সংখ্যা দিয়ে দুইটা দলকে কতটা আলাদা করা যায়?"

তাই আমরা কোনো model train করিনি। শুধু একটা সংখ্যা নিয়ে প্রশ্ন করেছি: "এই একটা সংখ্যাই কি উত্তর বলে দিতে পারে?"

যে সংখ্যাটা নিয়েছি

to_end  =  (track-এর শেষ ফ্রেম)  −  (window-এর anchor ফ্রেম)

মানে: "এই window-টার পর ওই পথচারী আর কত ফ্রেম ক্যামেরায় ছিল?"

AUC আসলে যা মাপে

সংজ্ঞাটা খুব সহজ: এলোমেলোভাবে একটা positive আর একটা negative তুললে — positive-এর সংখ্যাটা কত শতাংশ ক্ষেত্রে বড় হয়?

ছোট উদাহরণ

ধরুন মাত্র ৩ জন positive (to_end = 100, 250, 400) আর ৩ জন negative (40, 50, 60)। সব জোড়া মিলিয়ে দেখুন — মোট ৩ × ৩ = ৯টা জোড়া:

100>40 ✓   100>50 ✓   100>60 ✓
250>40 ✓   250>50 ✓   250>60 ✓
400>40 ✓   400>50 ✓   400>60 ✓        →   AUC = 9/9 = 1.0000

আমাদের আসল data-তে ঠিক এটাই

Negative সবাই ৩২–৬২, positive সবাই ৮৮–৬,৬০৬। তাই প্রত্যেকটা positive প্রত্যেকটা negative-এর চেয়ে বড়। জোড়ার সংখ্যা 1,648 × 3,258 = ৫৩ লাখেরও বেশি — এবং সবগুলোই সঠিক।

স্বাধীনভাবে পুনঃযাচাই করা: sklearn.metrics.roc_auc_score দিয়ে সরাসরি হিসাব করে পেয়েছি —
মূল পরিষ্কার data-তে AUC(to_end) = 1.000000, control-এর পর 0.777941।

এটাই diagnostic। আমরা প্রমাণ করলাম — model ছাড়াই, শুধু "ক্যামেরা আর কতক্ষণ চলবে" জানলেই ১০০% নিখুঁত উত্তর দেওয়া যায়।

৭. সমাধান ২ — Phase-Matched Control

মূল ধারণা এক লাইনে: একই পথচারী, একই ভিডিও, একই আচরণ — শুধু তাকে আমরা আগে গিয়ে দেখব।

আমরা কোনো নকল data বানাইনি, negative class বাদ দিইনি। শুধু কখন তাকাচ্ছি সেটা বদলেছি।

ধাপে ধাপে

ধাপ ১ — Positive-দের to_end জমা করলাম

1,648টা positive window-এর মান একটা তালিকায় রাখলাম। এটাই আমাদের লক্ষ্য-বণ্টন।

ধাপ ২ — Positive-দের কিচ্ছু করলাম না

তাদের সময় crossing ঘটনা দিয়ে বাঁধা। হুবহু আগের window রেখে দিলাম।

ধাপ ৩ — প্রত্যেক negative পথচারীর জন্য নতুন সময় বাছলাম

f0, fN = track-এর প্রথম ও শেষ ফ্রেম
hi     = fN - f0 - 15                  # সর্বোচ্চ কত পিছনে যাওয়া সম্ভব

if hi < 88:                            # track খুব ছোট
    বাদ দাও

target = positive তালিকা থেকে এলোমেলোভাবে একটা মান
te     = clip(target, 88, hi)           # যতটুকু সম্ভব
anchor = fN - te                        # শেষ থেকে te ফ্রেম পিছনে
window = ওখানকার ১৬টা পরপর ফ্রেম

৮৮ সংখ্যাটা এলোমেলো নয় — এটা positive-দের সর্বনিম্ন to_end, অর্থাৎ যেখান থেকে দুই শ্রেণীর একসাথে থাকা সম্ভব তার সীমানা।

একটা বাস্তব উদাহরণ

ধরুন রহিম একজন negative পথচারী, তার track ফ্রেম 1000 থেকে 1500।

পুরনো:   1000 ─────────────────────────────●── 1500
                                        anchor 1454  (শেষ থেকে ৪৬ ফ্রেম)

positive তালিকা থেকে এলোমেলোভাবে উঠল 250  →  নতুন anchor = 1500 − 250 = 1250

নতুন:    1000 ──────────────●───────────────── 1500
                        anchor 1250  (শেষ থেকে ২৫০ ফ্রেম)

রহিম একই মানুষ। একই ভিডিও। সে এখনো রাস্তা পার হয় না। শুধু আমরা তাকে ২০০ ফ্রেম আগে দেখছি — ঠিক যতটা আগে crossing-দের দেখি।

কারণ clip। Negative-দের track এমনিতেই ছোট। ধরুন positive তালিকা থেকে উঠল ৮০০, কিন্তু রহিমের পুরো track-ই মাত্র ৪০০ ফ্রেম। তখন বাধ্য হয়ে ৪০০-তে কেটে দিতে হয়।

আরও কমানো যেত? হ্যাঁ, কিন্তু দাম দিয়ে — MIN_TO_END ৮৮ থেকে ১৫৮ করলে আরও প্রায় ৪০% negative বাদ পড়ত; positive-দের track কেটে ছোট করলে তাদের সময়ও কৃত্রিম হয়ে যেত।

সতর্কতা: control arm-এ এখনো Holm/bootstrap চালানো হয়নি। তাই উপরের কথাটা point estimate-এর পর্যবেক্ষণ, পরীক্ষিত দাবি নয়। এটা চালানো এখনো বাকি — একটা ছোট কাজ, checkpoint গুলো ইতিমধ্যেই সংরক্ষিত।

এটা IDD-PeD-র নিজের paper-এর একটা স্পষ্ট দাবির বিপরীত (তারা লিখেছে সব crossing case-এ observation ও TTE দুটোই crossing-এর আগে)। Paper-এ এটা অভিযোগ হিসেবে নয়, তাদের প্রকাশিত ফাইল থেকে পুনরুৎপাদনযোগ্য পর্যবেক্ষণ হিসেবে লিখতে হবে। এটাই সবচেয়ে বিতর্কিত দাবি হবে বলে ধরে নেওয়া উচিত।

১০. Paper-এর গল্প

এই field-এর benchmark-এ একটা নয়, দুইটা মাপজোখের সমস্যা আছে।

প্রথম — Temporal contamination: যে ঘটনা predict করতে বলা হচ্ছে, সেটা crossing window-এর 67.9% ক্ষেত্রে input-এই দেখা যাচ্ছে।

দ্বিতীয় — Class-dependent sampling phase: negative-দের সবসময় track শেষ হওয়ার ঠিক আগে দেখা হয়, যা একাই AUC 1.0000 দিয়ে শ্রেণী আলাদা করে।

আসল কথা: প্রথমটার সমাধান দ্বিতীয়টাকে ছোঁয়ও না। দুইটাই নিয়ন্ত্রণ করলে সব model প্রায় 0.05 AUC হারায়, গাড়ির গতির প্রাধান্য উল্টে যায়, চারটা architecture-এর পার্থক্য এক seed SD-র ভেতরে মিলিয়ে যায়, আর একটা সাধারণ logistic regression চারটা neural network-কেই হারিয়ে দেয়।

এটা "আমরা ভালো model বানিয়েছি" ধরনের paper নয়। এটা "এই benchmark যা মাপে বলে দাবি করে, তা মাপে না" ধরনের paper।

১১. সীমাবদ্ধতা — সৎ তালিকা

এগুলো paper-এর Limitations-এ যাবে। কিন্তু §৮-এর সংখ্যাগুলো Results-এ যাবে, Limitations-এ নয়।

Control-এর নিজের সীমা

  1. একটাই seed (SEED = 42) দিয়ে negative আবার তোলা হয়েছে — পুনঃনমুনায়নের ভিন্নতা মাপা হয়নি।
  2. অবশিষ্ট separability 0.7779, 0.5 নয় — কমেছে, শেষ হয়নি।
  3. ১১৫ জন negative পথচারী বাদ পড়েছে, তাই population একটু বদলেছে (test set 541 → 476 পথচারী)।
  4. Control arm-এ significance test হয়নি — এগুলো এখনো শুধু point estimate।
  5. একটা বিকল্প ব্যাখ্যা বাদ দেওয়া যায়নি: হয়তো নতুন negative গুলো এমনিতেই কঠিন (দূরে, ছোট box) — timing নয়, দূরত্বই কারণ। এটা আলাদা distance-matched design ছাড়া আলাদা করা যায় না।

মূল কাজের সীমা

  1. কোনো equivalence margin আগে থেকে ঠিক করা হয়নি। "CI-তে শূন্য আছে" মানে "সমান" নয় — সেজন্য আগে থেকে δ ঠিক করে TOST লাগে (Bouthillier, MLSys 2021)।
  2. Power রিপোর্ট করা হয়নি। এই নমুনা আকারে "তাৎপর্যপূর্ণ নয়" ফলাফল স্বাভাবিক — প্রতিটা null পড়তে হবে "আমরা পার্থক্য ধরতে পারিনি" হিসেবে, "পার্থক্য নেই" হিসেবে নয়।
  3. Transformer-এর AUC সুবিধা capacity-matched নয় — 794,241 বনাম BiLSTM-এর 594,561 (1.34×), আর search budget 2.2×।
  4. Validation ছোট এবং বহুবার ব্যবহৃত — 634 window / 164 পথচারী, চারটা পরপর নির্বাচনে + threshold ফিটিংয়ে একই set। তাই সব validation সংখ্যা উপরের সীমা।
  5. Label track-স্তরের — একজন পথচারীর পুরো track-এর একটাই label, প্রতিটা window-এ ছড়ানো।
  6. একটাই test split (set03), এবং দিনের আলো, শুকনো আবহাওয়া, একটাই শহর।
  7. Cell-type সমতা মূলত Chung (2014)-এর পুনরাবৃত্তি — তিনি আগেই দেখিয়েছেন ছোট sequence-এ un-gated RNN gated cell-এর সমান। ১৬ ফ্রেম ঠিক সেই ছোট-দিগন্ত অঞ্চল।

শিরোনাম নিয়ে দুটো পরামর্শ

  • "intention" শব্দটার বদলে crossing action / outcome লেখা বেশি সঠিক — কারণ label আসলে PIE-র crossing attribute, উদ্দেশ্য নয়।
  • শিরোনামে "statistically rigorous" দাবি না করাই ভালো — Gesnouin (IV 2022) ইতিমধ্যেই Friedman + Wilcoxon–Holm ব্যবহার করেছে, BiPed ২০ initialisation-এর SD দেয়, MFT সব metric-এ ± দেয়। যা সত্যিই খালি আছে তা সংকীর্ণ: পথচারী-ভিত্তিক clustered resampling, equivalence margin, এবং তুলনীয় family-দের মধ্যে search budget সমান রাখা।

ক) পরিষ্কার leakage report-এ একটা ছোট অভ্যন্তরীণ টানাপোড়েন আছে: সে বলে "0টা window-এ crossing ফ্রেম", কিন্তু একই সাথে "1,648 জনের মধ্যে 12 জনের (0.7%) onset window শেষের আগে বা সমানে"। প্রধান দাবিটা (0/4906) সরাসরি cross == "crossing" গুনে পাওয়া, তাই সেটাই quote করুন।

খ) Zero-shot ব্যর্থতার দাবি rescale রূপান্তরের জন্য সত্য; raw-তে F1 0.244–0.268 (baseline-এর উপরে)। কোনটা quote করছেন স্পষ্ট করে বলুন, নইলে reviewer এটাকে cherry-picking বলবে।
এক লাইনে মনে রাখার কথা

Leakage ঠিক করার পরেও data-তে একটা লুকানো সংকেত রয়ে গিয়েছিল — শুধু "negative-দের কখন দেখা হয়েছে" সেটাই। সেটা সরালে সব model প্রায় 0.05 AUC হারায়, আমাদের সেরা model আর সেরা থাকে না, এবং গাড়ির গতির প্রাধান্যের গল্পটা উল্টে যায়।

এজন্যই এটা Limitations-এ লুকানো যাবে না — এটাই paper-এর সবচেয়ে শক্তিশালী প্রমাণ যে প্রথম সমাধানটাই যথেষ্ট নয়।

এই নথির সব সংখ্যা তৈরির সময় যাচাই করা। উৎস ফাইলের তালিকা §১২-এ।
